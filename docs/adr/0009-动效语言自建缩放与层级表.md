# 动效语言：自建缩放、四层时长表、两条硬护栏

M9（`v0.9.2`）要给全应用一套统一的动效语言，并且**第一次**把"用户关掉系统动画"这件事真正
接上。本 ADR 记录这套地基的决策、一条必须留着的已知风险，以及两条不能破的护栏。

## 曲线源与形状源分离

`LyraTheme` 只换 `colorScheme`，**不换** `Shapes` 也不换 `LyraTypography`：一换就要重走逐屏
截图的回归面，而本版的目标是动效不是外观。

计划里原写"改调 `MaterialTheme(colorScheme, MotionScheme.Expressive, Shapes(), LyraTypography,
content)`"——**这条做不到**。按 `javap` 实测本版锁的 material3 1.4.0：`MotionScheme` 接口、
`MaterialTheme(motionScheme = …)` 那个重载、以及 `MaterialExpressiveTheme` 全是 Kotlin
`internal`（字节码上看着像 public，那只是 `internal` 的编译方式），公开面上既读不到也换不进去。

而且就算能挂上，收益也有限：本项目实际用到的那批组件里只有 `NavigationBar` / `TopAppBar`
一族会读 `motionScheme`，`Chip` / `Slider` / `IconButton` / `Surface` **不读**。所以 Chip 与
Slider 的质感不会白送，必须在 `LyraMotion` 里自己写。

因此：弹簧常量（effects 临界阻尼 `3800/1600/800`、spatial 允许过冲 `800@0.6` / `380@0.8`）
直接从 material3 的 `ExpressiveMotionTokens` 抄进 `LyraMotion`。工具链升到 `motionScheme`
公开的版本后，**这里是唯一替换点**。

## 自建动效缩放（MotionScale）

> **本节初稿的判断是错的，已在实现中改正。** 原文写"Compose 的 `AnimationSpec` 时长不会
> 自动跟随系统设置"——实测**会**跟随（见下文"已知风险"，那条风险已经变成结论）。
> 保留这段是为了记下错误本身：一个看起来理所当然的前提，量一次就知道真假。
> 现在的实现与验收以 `../releases/v0.9.2/CHANGELOG.md` 的"决策 1"为准。

- 读 `Settings.Global.ANIMATOR_DURATION_SCALE` 与 `TRANSITION_ANIMATION_SCALE`，**取较小值**，
  再夹紧到 `[0, 1]`（`MotionScale.clamp`）。
- 经 `MotionScaleProvider` 挂成 `LocalMotionScale`。语义**不是**"用户想要的倍率"，
  而是"**该写进 spec 的乘数**"= 想要的倍率 ÷ 平台已经乘过的那一份（`MotionScale.specMultiplier`）。
- `0`（以及 ≤ 0.1 的极小值）不是"很短的 tween"，而是 `snap()`：给 0ms 的 tween 仍要排一帧回调，
  用户给的是"别动"这个表态。
- 读不到（负值 / `NaN`）按 `1` 处理——不能因为一个解析异常把界面变成幻灯片。

两个取舍值得写下来：

- **取较小值而不是平均**：两个开关是独立的两件事，用户把任一个调到 0 都是明确的"别动"表态，
  平均会把这个表态洗掉。
- **只认到 1，1.5/2.0 不放大**：调大系统动画时长的人要的是"系统动画更慢"，而本项目里大量动画是
  反馈类（按压、勾选、图标 morph），放大只会让手感变迟钝。

### 已证实：平台自己已经乘过一次（本版的实际改动）

反编译 `androidx.compose.animation:animation-core` 1.11.4 与 `androidx.compose.ui:ui` 1.11.4：

1. `SuspendAnimationKt.doAnimationFrameWithScale` 的逻辑是
   `durationScale == 0 ? animation.durationNanos : (frameTimeNanos - startTimeNanos) / durationScale`，
   而 `durationScale = coroutineContext[MotionDurationScale]?.scaleFactor ?: 1f`。
   **这是 tween 与 spring 共用的那条帧循环**，所以两类动画都会被缩放，0 时直接跳到终点。
2. `WindowRecomposer_androidKt.getAnimationScaleFlowFor` 注册 `ContentObserver`，并在
   recomposer 创建时读 `Settings.Global.animator_duration_scale`，喂给 recomposer context
   上的 `MotionDurationScaleImpl`。
3. 但它**只读 `animator_duration_scale` 这一档**（不读 `transition_animation_scale`），而且
   **不夹紧上限**（2.0 就是两倍长）。

实测确认（模拟器上的真应用窗口，同一动作）：`animator` 1.0 → 950–980ms，2.0 → 1740–1790ms。
我们的 `clamp` 在 2.0 时必然输出 1.0，所以那 1.85 倍只能来自平台。

**所以平台真正缺的只有两件事**：不读 transition 那一档、不夹上限。本层的职责从"实现缩放"
改成"补这两件事"，做法是除掉平台那一份再让平台乘回来：

```
multiplier = clamp(animator, transition) / platformFactor(animator)
墙钟时长   = 基准 × multiplier × 平台 factor = 基准 × intent
```

`animator = 1.0`（默认档）时 `multiplier = 1.0`，所有动画与改动前一字不差——这是本次改动
风险为零的原因。

仪器测试**量不到**这条链：把 `animator_duration_scale` 置 0 后，一个
`animateFloatAsState(tween(2000))` 走 200ms 仍只到 ~0.1。测试框架自带 recomposer 与时钟，
与生产的窗口 recomposer 不是同一条链。要量就得跑真应用窗口，再"数帧"或"看墙钟"。

**弹簧用等价的刚度换算**：周期 ∝ `1/√stiffness`，所以"时长乘 s"等于"刚度乘 `1/s²`"
（`MotionScale.springStiffnessScale`）。这替掉了初稿"弹簧没有时长可乘，只能整条播或不播"的说法
——那个说法在"我们自己乘时长"的前提下成立，在"平台乘时间轴"的前提下不成立。

**没被治到的一个口子**：`Modifier.animateItem()` 内部那两条 spring 由 foundation 自己构造，
我们改不到它的刚度，所以它在 `animator = 2.0` 时仍会被平台放大。`lyraAnimatedItem` 只保住了
"关掉动画时整条不播"。根治要传显式 spec，本版不做，记在 CHANGELOG 的"已知残余"。

## 四层时长表

| 层级 | 进入 / 退出 | 用途 |
| --- | --- | --- |
| micro | 100 / 120ms | 按压形变、图标 morph、♥ 弹跳 |
| small | 150 / 200ms | 页码指示器、文字交替、♥ 交叉淡出 |
| medium | 250 / 300ms | 列表增删让位、Snackbar、加载揭示、主题涟漪 |
| large | 350 / 450ms | 跨页面的连续性（M10 共享元素）；`BlurBackdrop` 现有 450 保持 |
| 路由转场 | **280 入 / 240 出（保留现值）** | 播放页升起与缩回 |

路由转场单独一档而不是归进 large：这组数是三轮真机验收调出来的，本版不动它。层级表把它钉在这里，
是为了让"不动"这件事有地方记录，而不是靠注释散在三个文件里各自解释一遍。

## 两条硬护栏

1. **全屏路由位移禁止使用会过冲的 spatial spec。** 过冲意味着全屏界面在某一帧越出容器边界，
   露出的就是底下的画面。继续用现有那两条显式 spring（`LowBouncy` 进 / `NoBouncy` 出），
   **不委托给 expressive spatial**；过冲只准给小元素（♥、播放键这类 one-shot pop）。
2. **禁止动画任何参与布局的属性**：`size` / `width` / `height` / `padding` /
   `verticalArrangement` 一律不动，只走 `graphicsLayer` 的 scale / alpha / translation。
   来历是 `LyricPanel` 那条教训——换行时改字号会让行高在动画中途变化，而滚动目标正是"滚到这一行"，
   目标自己会动，看起来就是整屏抖一下。本版把这条推广到按压形变（只缩 `scale`）与页码指示器
   （药丸用 `scaleX` 从 7dp 长到 18dp，而不是动画 `size()`）。

## 转场注册去重

`LyraApp.kt` 里那四个转场参数此前**一字不差地抄了 13 遍**，抄错一条的表现是"某一页底下的 Tab 页
跟着一起滑"，而且很难发现。现在收成 `NavGraphBuilder.lyraDetailRoute(route, …)` 一处，
分类由纯 Kotlin 的 `LyraRoutes`（`RouteKind` + `DETAILS` 表）回答，因此可以写成 JVM 单测。
播放页保留独立注册——它是"从迷你播放条长出来"的另一套观感。

## 备选方案

- **换 `MaterialExpressiveTheme` / `motionScheme`**：本版锁的 material3 里是 internal，做不到；
  且只有 `NavigationBar` / `TopAppBar` 一族读它，换来的统一度不足以覆盖本项目用到的组件。
- **读 `Window.animationScale`**：那是窗口属性，在 Composable 里要穿过 Activity window 才能拿到，
  和 `Settings.Global` 里的值是同一件事，多一层耦合。
- **不做自建缩放，直接依赖平台**：平台只认 animator 一档、不读 transition 一档、还不夹紧上限。
  初稿以为"本项目的动画从来没跟随过系统开关"，实测证明**恰好相反**——它一直在跟随 animator 那一档；
  缺的是另外两件事，所以本层是"补齐 + 除重"，不是"从零实现"。
- **每处各写 `tween(230)`**：参数散在二十来个文件里时"这里弹一下那里滑一下"的割裂感没法收敛，
  而且系统缩放要生效就必须逐处改——那正是本次要消灭的东西。
- **给每个动画加常驻动效（呼吸 / 进度环）**："按钮在闪"的观感收益不抵它的代价：常驻动画每帧
  都要自绘，`CHANGELOG.md` 里已经实测过它把刷新率从 60 拉到 120，与歌词扫光叠在同一页上
  会直接污染 Jank 预算。

## 后果

- 新增任何动画都必须先选一档 `MotionTier`；层级表之外的基准时长走 `MotionSpec.durationMsOf`，
  不允许再出现"第二份实现"。
- 弹簧走刚度换算（`springStiffnessScale`），但 `scale ≤ 0.1` 时仍然**整条不播**——
  刚度再高也要排一帧，而用户给的是"别动"。`lyraPressable` / `lyraReveal` / `lyraAnimatedItem`
  与 `LyraMotion` 的四条转场都按这条实现，新写的组件要照做。
- `SnackbarHost` 在 material3 1.4.0 里只有 `hostState` / `modifier` / `snackbar` 三个参数，
  **过渡不可参数化**，所以 Snackbar 走 material3 自带过渡：它**会**跟随平台的 animator 那一档，
  但**不**跟随我们的 `transition_animation_scale` 与上限夹紧。这是本版已知的缺口，
  不为了它自己重写一个 `SnackbarHost`。
- 关掉系统动画后，详情页进出变成瞬时。观感上是"没有动画"，而不是"很快的动画"。
- `Modifier.animateItem()` 内部那两条 spring 由 foundation 自己构造，改不到刚度，
  所以它在 `animator > 1` 时仍会被平台放大。要根治得传显式 spec，本版留作已知残余。
- 需要复核的时点只剩一个：工具链升到 `motionScheme` 公开时（`LyraMotion` 的弹簧常量）。
  双重缩放那条已经量完并修好，结论在 `../releases/v0.9.2/CHANGELOG.md` 的"决策 1"。
