# crossfade 用双播放器加共享缓存，会话播放器不换人

M2 要求两首歌之间做真正的重叠淡入淡出，而 MediaSession 只能绑一个播放器：通知、锁屏、
媒体键、流体云读的都是它。我们决定让会话播放器（primary）自始至终持有队列与会话，
另起一个不抢音频焦点的副播放器（secondary）在淡入窗口里提前播下一首，淡入结束后
primary seek 到副播放器的位置接管，副播放器退场；两个播放器共用同一个 SimpleCache，
副播放器淡入期间写下的字节就是 primary 接管时的缓存命中。

## 备选方案

- **会话换绑 / ForwardingPlayer**：淡入结束把 MediaSession 指向另一个播放器。控制器连接、
  时间线与元数据的缓存状态都要跟着迁移，出问题的面比收益大。
- **单播放器"淡出再淡入"**：实现只要几十行，但中间有一段静音，那不是 crossfade。
- **DefaultPreloadManager 预热下一首**：能省掉副播放器，但要改 media source 工厂与队列
  所有权，且与"地址惰性解析"的既有决定冲突得更深。

## 后果

- 淡入的这几秒里会话播放器还停在上一首，系统媒体界面的标题与封面会晚一个淡入时长
  （默认 4s）才切过去。想提前切只能改 MediaSession 上报的 PlayerInfo，未做。
- 交接不留痕迹的前提是共享缓存命中；缓存被清空或网络极慢时，引擎等 primary 就绪期间
  由副播放器继续出声，超过 8s 才放弃（留一个可闻断点，好过会话播放器一直静音）。
- 播放会往 cacheDir 写最多 128MB 的 LRU 缓存。重播同一首不再打音源，因为缓存命中时
  上游（含惰性取址）根本不会被打开。
