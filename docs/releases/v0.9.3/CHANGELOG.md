# v0.9.3 变更记录（M10 播放连续性）

本版做的是**播放这件事本身的连续性**：从哪张封面点的，封面就飞到哪去；翻页时页码跟手；
拖 seek 松手时手指的速度决定落在哪一秒。规格与切片见 [`PLAN.md`](PLAN.md)，
决策见 [`../../adr/0010-共享元素转场.md`](../../adr/0010-共享元素转场.md)，
逐片实现提示词见 [`PROMPTS.md`](PROMPTS.md)。

状态：**代码与真机逐片目视均已落地（010–014）**，见本文末「真机验收」一节。
分支 `dev/v0.9.3`，版本 `0.9.3` / `versionCode 8`。**已 squash 合入 `main` 并打 tag `v0.9.3`。**
这一笔同时把 v0.9.2 的真机补录带进了 `main`（那轮量的是 0.9.3 的包，见
[`../v0.9.2/CHANGELOG.md`](../v0.9.2/CHANGELOG.md) 开头那句说明）。
那一轮同时把 v0.9.2 留的"重新收紧条件 ②"量完了，**结论与本文当初的猜测相反**：
唯一一处 Jank 门槛不过的锅不在共享元素，在 v0.4.0 就有的播放页模糊背景。

## 摘要（面向用户）

- 点迷你播放条进播放页：那块 44dp 的小封面**飞成**播放页的 230dp 大图（010）；返回时飞回去。
- 点歌单 / 榜单 / 专辑 / 自建歌单的封面卡片：封面飞到详情页头的 96dp 大图上；
  返回时飞回**来路上那一张**卡片（011）。收藏的歌单那行 48dp 的小封面也参与。
- 「我喜欢」「本地音乐」不参与：它们的页头是"第一首曲目的图"，那是代理，不是目的地的封面。
- 图还没加载完、落点找不到、系统动画缩放关掉——这三种情况一律不飞，退化成原来的硬切，
  绝不插值一张占位图。
- 播放页左右翻页时页码**跟手**：手指拖到哪，药丸就长到哪，不再"翻完才跳"；
  封面另加一层 8% 页宽的落后视差（012）。歌词页不参与视差。
- 拖进度条**一甩**会甩得更远：松手时按释放速度往前投影，最多 ±3s，落点就是真实落点
  （不回弹）。拇指上方那枚时间气泡显示的是"这一甩会落到哪"，不必先松手再猜（013）。
  快速拖一段、**停一下**再松手 = 不投影，就停在手指处；键盘方向键与读屏设值也不带投影。
- 迷你播放条那两行曲名 / 艺术家只在**换到另一首歌**时交替一次；同一首歌补封面、
  时长回来、播放暂停翻转，一个字都不动（014）。

## 决策 1：共享元素用自写覆盖层，不用 `SharedTransitionLayout`

ADR-0010 原文写的是"用 `androidx.compose.animation` 里的共享元素设施"。落地换成了自写的
整屏 `Canvas` 覆盖层，**设计一个字没改**（覆盖层 + 两端登记 + 位置 / 尺寸 / 圆角插值），
改的只是库。理由、以及那条性能入场费（登记表不可观察、隐身走绘制期）都在
[`../../adr/0010-共享元素转场.md`](../../adr/0010-共享元素转场.md) 的"落地修正"一节。

方案 B（fade-only）**从未启用**：预定的失败现象"两套位移打架"没有出现，
因为终点矩形是**现量**的（飞行期间每帧从 `LayoutCoordinates` 读），目标页在路由转场里滑，
封面就跟着它滑。这条不是推理，`CoverAnchorTracksLayerTranslationTest` 把它钉住了。

## 决策 2：010 里那层"补报位图"是多余的，删

010 写过 `CoverFlightState.refreshArtwork()` + 一个 `SideEffect`，理由是"换曲时封面换了图
但布局没变，`onGloballyPositioned` 不会重跑，登记表会留着上一首歌的位图"。

**这个理由是错的**：把 `SideEffect` 注释掉之后，011 那 7 条像素测试全过，包括专门测换图的
`aCardWhoseCoverWasSwappedFliesTheNewCover`。真正发生的是——那行 modifier 读的 `artwork`
是本次重组捕获的值，捕获一变挂上去的就是**新的 lambda 节点**，Compose 会重跑 placement。
所以登记表只留 `onGloballyPositioned` 一个写入点，补报路径整条删掉。

这件事值得记一笔的原因：那段代码的注释写得很有说服力，而且它**确实没被证伪过**——
直到 011 有了能测换图的测试。判据现在留在测试的 KDoc 里，防的是有人按直觉把它加回来。

## 决策 3：页码"几何跟手、身份跳变"

012 里唯一一处观感取舍：药丸宽度与邻居让位**每帧从连续页位置现算**，
而颜色**仍由离散的 `currentPage` 驱动**。

几何回答的是"这块图现在有多像当前页"，那是连续量；颜色回答的是"哪一页是当前页"，那是身份。
半程时把两枚都染成中间色，读起来是"这两页都是当前页"——不是信息。
所以 `PageIndicator` 收两个来源：一个组合期读、一个绘制期读，**不许合成一个**。

顺带一条必须留住的实现约束：偏移量只在**绘制期**读（`() -> Float` 进 `graphicsLayer`）。
组合期读它会让拖动的每一帧重组指示器那一行与封面那一摞，而翻页正压在
"滚动 + 转场首帧"那两个 Jank 场景上。这条现在有测试钉住（见"验证"最后一条）。

## 决策 4：视差量不是"真机上定"的，是被上下界夹出来的

PLAN §012 原文写"具体数值在真机上定"。**实际没有**，两个已有的界把它定了：
横向余量（封面 230dp、页边距 20dp ⇒ 两侧各约 45dp 可用）给上界，
JVM 那条 `parallaxStaysSmallEnoughToReadAsDepth` 把常数夹在页宽 5%–12%（满程）与 ≤ 8%（中点）。
真机目视因此只剩"好不好看"要判，不再兼着"选一个数"。

## 决策 5：013 的落点基准从 tap 换成"同一手势在 scale = 0 下的落点"

013 原先每条惯性测试都先在同一位置 **tap** 一次，拿它当"手指处"的实测基准，理由是
"不抄 material3 的换算"。第一条真跑起来就露馅了：`pausingBeforeReleaseCancelsTheInertia`
量到手指 15000ms、实测 14163ms —— **差 837ms**，而那条测试的容差写的是 300ms。

查下去这不是 bug：tap 走 `sliderTapModifier` 的 `onTap → dispatchRawDelta(0f)`，靠
`pressOffset` 做**绝对定位**；拖动走 `horizontalDrag` 的**增量累加**（`rawOffset += delta`）。
两条路径换算不同，同一目标位置本来就能差这么多。**拿两条不同的路径互比，测到的差里
混着换算差，不是惯性。**

所以基准改成**同一条手势在 `scale = 0` 下的落点**：`projectSeek(animate = false)` 按
ADR-0009 连投影一起跳过，那一个数就是这条手势自己的"手指处"。两条路径完全相同，
差出来的只剩惯性，判据反而收到 1.2s（比原来对着 tap 的 300ms 更紧，因为它终于测对了东西）。

`rawOffset` 会不会把两次手势串味？不会：`down` 设 `pressOffset = to - rawOffset`，
第一次 `dispatchRawDelta(delta)` 后 `rawOffset = downX + delta`——**起点是按下点，与历史无关**，
所以两次 fling 相减是确定的，不是碰运气。

顺带量到一条 material3 的真实行为，写下来而不是当成 bug 修：**按住不动、一步都不挪，
不会产生任何一次 seek**（探针里 `seeks = []`）。源码里 `dispatchRawDelta` 有个
`if (scaledUserValue != this.value)` 的守卫，值没变就不调 `onValueChange`；而
`onValueChangeFinished` 只在 `onDragStopped` / `onTap` 里调。所以"按住 → 直接抬手"
这条路径根本不经过投影代码。这不是缺陷，是"用户没选任何新位置"的正确表达。

## 决策 6：014 的"关掉动画"——先量到"两帧"，修完之后是"一帧"

`reducedMotionSwapsTheTitleInOneFrame` 第一次跑就失败：`expected:<0> but was:<1>`。
逐帧探针量到的事实是——scale = 0 时旧曲名在**第 1 帧**（t+16ms）还在、**第 2 帧**（t+32ms）才没；
而 scale = 1 时到 t+96ms 两份都还在（micro 档的退场本来就是 120ms）。

当时据此把保证放宽成"两帧之内"，理由是 `None togetherWith None` 只让那一份**不播动画**、
收回节点仍要等 `AnimatedContent` 下一次整理子内容。

**这个放宽只活了半天，而且方向是错的**：那"多出来的一帧"里新旧两份是**同画**的（见决策 8），
不是"晚一帧到终态"。修成"关掉动画就不进 `AnimatedContent`"之后，旧内容在第 1 帧就已经没了，
判据因此收回到 `reducedMotionDropsTheOldCopyOnTheFirstFrame`。

对照组 `realSongChangeKeepsBothCopiesWhileSwapping` 在**同一个第 1 帧**断言"开着动画旧的还在"，
另外多判第 2 帧一次（micro 档退场 120ms，那时才 32ms，中间期确实存在）。
两条在同一个帧位相比，差出来的才是"有没有动画"，而不是"我多按了几帧"。

## 决策 7：`slideInVertically` 到底动不动布局——这条核实了

014 落地时没核实过 `AnimatedContent` 里 slide 的落位方式，工单因此只敢写"由测试量"。
现在读了 animation-android 1.12.1 的 `EnterExitTransition.kt`：slide 走
`placeWithLayer(offset.x, offset.y, 0f, layerBlock)`，而容器上报给父级的尺寸是
`layout(currentSize.width, currentSize.height)`，**不含 slide 位移**。
纵向位移因此只挪绘制层、不撑高那一行——ADR-0009 护栏二在这里是满足的，
`swapDoesNotRampTheContainerWidth` 量的也确实是这件事。

## 决策 8：`None togetherWith None` 不是"直接到终态"——一处真实回归，005 与 014 各中一次

写 014 时照着 005 的 `PlayPauseGlyph` 抄了这句：

```kotlin
if (!MotionSpec.shouldAnimate(scale)) EnterTransition.None togetherWith ExitTransition.None
```

注释里写的是"关掉动画就同帧换字"。**这个说法是错的**，而且错在两处代码里。

第一条设备测试就红了：`expected:<0> but was:<1>`。逐帧探针量到 scale = 0 时旧内容在
第 1 帧（t+16ms）**还在**、第 2 帧才没。再做一次像素差分探针，性质比"晚一帧"严重得多——
第 0 帧既不像旧内容也不像新内容（静止A↔第0帧 1863px，第0帧↔稳定态 1800px，
而第 1 帧↔稳定态 0px）。**那一帧同时画着两份文字**：迷你条上闪一下"两行字叠在一起"。

回到 005 用同一个探针量播放/暂停图标，症状一模一样（静止↔第 0 帧 413px、第 0 帧↔稳定态 198px）：
按钮会闪一下"三角形压在两根竖条上"。

机制上说得通：`EnterTransition.None` / `ExitTransition.None` 只是让那一份**不播动画**，
`AnimatedContent` 仍要为退场排一次帧、下一轮整理子内容时才把它收回。ADR-0009 把"0"定成
**直接到终态**，这个写法办不到。

修法不是换个 spec，是**关掉动画时压根不进 `AnimatedContent`**：

```kotlin
if (!MotionSpec.shouldAnimate(scale)) {
    SongLines(text, modifier)   // 或 Glyph(isPlaying, ...)
    return
}
```

两处的终态内容都抽成了独立 composable（`SongLines` / `Glyph`），开不开动画画的是同一个东西，
所以"到终态"与"交替结束"逐像素相同——这一点现在分别由
`reducedMotionNeverPaintsBothCopies` 与 `playPauseGlyphPaintsOnlyTheEndStateWhenMotionIsOff`
用像素差分钉住，判据都写成"第 0 帧与稳定态差 0 像素"，而不是"第 0 帧与旧内容不同"
（后者在同画两份时照样满足，正是第一版测试漏掉这个 bug 的原因）。

`LyraMotion.songLineSwap` 里那条 `shouldAnimate` 早退随之删掉：调用方已经挡在前面，
留着反而像"这个函数也能处理 scale = 0"，而它不能。

**005 的工单为什么没抓到它**：`MotionScaleUiTest` 的类注释当时明写着
"♥、播放/暂停、按压形变的'瞬时'体现在 graphicsLayer 的 alpha/scale 上，语义树里看不到——
为它们造断言只能断言到'点击有没有生效'"。这句话对 alpha/scale 是对的，但它把
"内容还在不在树上"也算成了不可观察，于是这一类缺陷在整个 M9 里**没有任何一条断言覆盖**。
现在有了：像素差分能看，成本是两次截图。那条类注释已经改掉。

♥ 收藏按钮这里原本写的是"没有这个问题"——那句话是**推理**出来的，而且推理错了。
推理的前半句没错：它不用 `AnimatedContent`，两张图常驻叠着走 `alpha(1f - fill)` /
`alpha(fill)` 互补淡入淡出，所以结构上不会出现"两份内容同画"。但"晚一帧到终态"是另一回事：

给 ♥ 加同一条像素测试之后**第一件事它就红了：第 0 帧与第 1 帧差 1525 像素**，
也就是实心那一档晚了一帧才到。原因与 `AnimatedContent` 无关。

**这里当时给的解释是错的，而且错了一次**：第一版修法写成
`if (shouldAnimate) tween(...) else snap()`，注释跟着写"是 `tween(0)` 的锅——时长为 0 的
tween 仍要先排一次起始值"。改完再跑，**那条测试仍然是红的，差分数字一个像素都没变（1525）**。
所以 `snap()` 并不能让它当帧落地，"晚一帧"发生在比 spec 更前面的一步：
`animateFloatAsState` 把目标值交给协程里的 `Animatable` 去追，而那个协程**在本次组合提交之后**
才被调度——第 0 帧画出来的必然还是旧值，无论 spec 是 `tween(0)` 还是 `snap()`。
`snap()` 只是保证它一旦跑起来没有中间值，救不了那一帧的调度时机。

真正的修法与前两处同一形状：关掉动画时**不读动画值**，直接取终值
（`val fill = if (shouldAnimate) animatedFill else if (favorite) 1f else 0f`）。
改完之后 `heartReachesTheEndStateOnTheFirstFrameWhenMotionIsOff` 从 1525 归 0。
这条结论值得单独一句：**"当帧到终态"这一类要求，靠给动画换一个零时长 spec 是办不到的**，
`AnimatedContent`、`animate*AsState` 两个 API 上各验过一次。

这条教训的形状值得单独记：**"某处没有这个 bug"这种话只有在量过之后才能写**。
上面那句"核过"我确实核了源码，但核的是我认为relevant 的那一半（有没有第三份内容），
没核另一半（终值哪一帧落地）。三处像素测试里有一处是加上去当场就红的——那一条才是它存在的理由。

2. 歌词换行的强调值原本写的是裸 `tween(EMPHASIS_MS = 320)`，**连 `LocalMotionScale` 都不读**。
   这一处不在本版的任何一片里（M3 就有），性质上是 002 那条"让系统动画缩放真正生效"的漏网，
   不是新引入的回归。基准 320ms 保持不变。

   **这里有一句我写错了，当场用库源码推翻**：先写的是"用户把系统动画调到 0，只有歌词还在
   慢慢放大淡入 320ms"。读了 animation-core 1.12.1 的 `SuspendAnimation.kt` 才知道不成立——
   `doAnimationFrameWithScale` 里 `durationScale == 0f` 时直接给
   `playTimeNanos = anim.durationNanos`，也就是**动画在自己跑到的第一帧就落到终值**，
   根本不会走 320ms。所以真实的漏网只发生在 `transition_animation_scale = 0` 而
   `animator_duration_scale` 仍为 1 这一档：平台只读后一个（工单 002 已经量实），
   于是我们判定的 intent = 0 完全没作用到这一处，歌词照样慢 320ms。
   另一个后果是"晚一帧"在这一处依然存在（终值要等动画协程跑到的那一帧），与 ♥ 同形。

   **"不吃缩放"这半句是代码可证的**（改前那一行里没有任何 `scale`），
   但**"晚一帧"这半句没量**：换行的同时 `LaunchedEffect(activeIndex)` 还要
   `animateScrollToItem(activeIndex)` 让整列表滚动，两次截图相减分不清"强调值晚了一帧"
   与"滚动本身在动"。要干净地量就得先把滚动钉住，那已经是在改歌词页的行为而不是在测这一处。
   所以修法照同一个形状改了（关掉动画就不读动画值），并**明确标注为未量**，
   与 008 / 009 / 010–011 同一档，而不是写成"已修已测"。

量到的这两处（♥ 与页码颜色）都是"晚一帧"而不是"叠字"，成因同一个：`animate*AsState` 把目标交给协程里的
`Animatable`，而协程在本次组合提交之后才跑——**判据只有一条**：关掉动画时不许读动画值。
歌词那一处按同一条判据改了，但没量（理由见上），所以它算这条判据的**推论**而不是**证据**。

3. `BlurBackdrop` 与歌词是同一个毛病（裸时长、不读 `LocalMotionScale`），**但这一处没改**：
   计划原文与 ADR-0005 都把"450ms 交叉 + radius 不动"列为保持项，动它等于推翻一条已验收的观感
   约束，该单独拍。**这一处留给用户决定，不在本版擅自做。**要改的形状也是现成的：那个
   `else` 分支（没有旧图层时）已经是"直接上新图、alpha 给 1"，scale = 0 时走同一条即可。
   同一页里还有歌词**扫光**的 `tween(POLL_MS)`：那个也不吃缩放，但它是"跟播放进度走的进度指示"
   而不是"状态变化的过渡"，snap 掉等于取消扫光——判定为不属于缩放的对象，明确不动。

值得记的一点：008 一开始就写对了（注释原话是"连一帧的 alpha=0 都不该有"），
005 却把同一个意思写成了 `None togetherWith None`。**同一份 ADR 里同一句话，
落到两种 API 上就有一半概率被实现错**——所以这一类现在靠像素差分兜，而不是靠读注释。

## 已修：`dropsLatePageFromSupersededLoadMore` 不是"偶发"，是测试自己没等

本版记过两次：011 收口时全量跑到 146 条第一次失败，012 收口时全量跑到 155 条又失败，
而**单独跑每次都过**。上一节（原文见 git 历史）把它记成"时序敏感"，
**那个判断是错的**——真实原因在测试自己的等待条件上：

- 等重载落地的判据写的是 `page == 1 && songs.size == PAGE && !loading`，
  而这三个条件在 `loadMore()` 进行中**就已经成立**（翻页写的是 `loadingMore`，不是 `loading`，
  `page` 要到响应合并才变）。于是这一句 `first { }` 等于没等，测试立刻往下读状态，
  读到的是 `loadMore()` 自己写下的 `loadingMore = true`，断在
  "也不许把新这次加载标成正在翻页"那一句上——**断言的哪一条先响，正好指回判据少了哪一项**。
- 收尾用 `kotlinx.coroutines.yield()` 也挡不住：测试协程在 instrumentation 线程，
  VM 的协程在应用主线程，`yield()` 只让**本线程**的调度器转一圈，等不到对面那条线程的续跑。
  现在换成 `InstrumentationRegistry.runOnMainSync { }`，要的正是"主线程已排队的活儿都跑完了"这个屏障。

判据补上 `!loadingMore`（重载那一次 update 是把 `loading` 与 `loadingMore` 一起写回的），
屏障换成 `runOnMainSync`，之后**全量跑 155 条 OK**、单独连跑 6 次全过。

为什么"单独跑必过"会掩盖它：单独跑时主线程空闲，重载的那次 update 赶在读状态之前落地；
全量跑时主线程忙（前后都是建了 Compose 规则的用例），就赶不上。**同一份代码在两种跑法下
结果不一致，本身就是"等待条件写错了"的信号**，不是环境噪声——这条判据值得记住。

## 订正：这一轮量下来，模拟器比文档里写的能用

上面这段（以及 012 / 013 工单里的同一句话）有**两处说法是错的**，这一轮做模拟器逐屏走查时撞出来的：

1. **"模拟器上没有音源"——不成立。**酷我源在模拟器上能出地址、能播、能出封面：
   这一轮实际播了 NEON / 无奈的思绪 / 天龙八部之宿敌 / 大漠长明 四首，
   迷你条那 44dp 的封面是真的（所以 010 的起飞条件在模拟器上就满足），
   歌词页也拿到了中韩对照的逐行歌词。
   当时那句"模拟器没有音源"多半是把"没有本地音乐权限/没有导入音源"当成了"远端也不行"。
2. **"`screenrecord` 每帧字节相同"——结论对、理由错，而且错得会让人放弃一个本来能用的取证手段。**
   量出来是**帧率**问题不是"内容不变"问题：一段 `--time-limit 4` 的录像
   `nb_frames = 5`、`duration = 3.576s`，也就是**约 1.4fps**。
   静止画面时逐帧字节确实相同（那是没东西要画），但**动画照样被抽到**：
   一次"我喜欢 → 播放页"的路由转场（280ms）就被抓到了一帧中间态（两页同屏、各画一半）。

   所以真正的边界是按**层级**分的，不是"模拟器录屏一律不可用"：
   1.4fps 意味着一帧约 700ms，**micro（100/120ms）与 small（150/200ms）两档必然抽不到**
   （实测点一次 ♥，整段录像里只有 3 帧有变化、差分 89/43/56 像素，全是歌词扫光，
   150ms 的交叉淡出与弹跳一帧没落下来）；
   **medium（250/300）与路由转场（280/450）偶尔能抽到一帧**，但"偶尔"不能当验收手段。
   结论保持不变——005 / 009 / 010 / 013 / 014 的中间帧仍要真机录屏——
   但**理由要换成"帧率不够"而不是"模拟器录不出动画"**，否则下次有人会拿它去试 large 档然后被误导。

   这一轮又量了一次，上面那句"结论保持不变"**对 010 要放宽**：
   把同一趟来回重复六次（`build/walk/f010b.mp4`，13.04s / 46 帧 ≈ 2.8 有效 fps），
   封面命中缓存之后 large 档真的抽到了多帧中间态——`h089` 是播放页刚进来、大图位还空着，

| Tab（对照） | 3.69 / 6.26 | 0.94 / 3.51 | 2.52 / 3.17 | — |

**读法**：CPU 侧两条几乎一样（1.09 vs 0.94），差的全在 GPU 侧（7.01 vs 3.30，p95 14.51 vs 4.42）。
共享元素覆盖层本身很便宜——它只在 `Canvas` 绘制里读进度、整段飞行不重组，
这条成本在"详情"那一行里已经付过了，而那一行是 0.83%。
多出来的全部是播放页那层 26dp 的**全屏 `RenderEffect`**。

**归因核实（这一步不能省，否则就是把锅甩给一个没动的东西）**：

- `git diff 088dfe3 HEAD -- .../BlurBackdrop.kt` → **0 行**，M9 tip 与 HEAD 字节相同；
- `git log --diff-filter=A` → 它由 `dd3d68b`（M3 切片 4）引入，`git tag --contains` 显示
  **v0.4.0 就有**；
- M10 对 `ui/motion/` 的 diff 里**没有**任何 `expandFromBar` / `collapseToBar` / `ROUTE_*` 改动，
  播放页那条转场的数值一个字没动。

所以 5.66% 不是"共享元素把转场拖慢了"，而是**这条路由本来就一直比别的转场贵**，
只是 v0.9.2 之前从没量过它——当时场景 A 只切 Tab，压根走不到 `CoverFlight`。
本轮为了分开这两个变量，专门给脚本加了 `Detail` 模式（有共享元素、无模糊）。

**因此条件 ② 的答案是"量完了，不需要为共享元素改任何东西"**：
共享元素那条路由（歌单卡片 ↔ 详情）超预算的帧只有 1 帧，而**它也是冷帧**
（118 号，前帧间隔 133ms）——按忙帧口径是 **0/116 = 0%**，与 Tab 对照同一档。
（原来这里写的 0.83% 是"全 120 帧里 1 帧"，同一个口径错误，一并订正。）
**但**播放页那条 5.66% 这个数是真的，**它当时的归因是错的**——
错在把"墙钟超过 16.67ms 的帧"当成了"转场动画正在跑却画不完的帧"。
逐帧看这 9 帧的**前帧间隔**之后：没有一帧落在连续渲染段内部，
其中 6 帧是孤立帧、2 帧是短段头、1 帧是采集窗口的第一帧
（最后这一帧是唯一 CPU 重的，形状上反而像一次转场的第一帧——它不能排除）。
详见下面「决策 9 的订正」。

`BlurBackdrop` 更贵的结论**仍然成立**，但成立的证据换了一条：忙帧里 GPU 段中位
6.99ms（无模糊的详情同位置 3.27ms），按 120Hz 一档 8.33ms 的预算判，
播放页忙帧超预算 **50/109 = 45.9%**，详情页 **3/116 = 2.6%**。
它是一笔**先于 M10 存在的性能债**，本版没有顺手修它——理由见下。

顺带一条让上面那个 GPU 归因更稳的观察：**中位数对冷帧污染不敏感**。
全 120 帧算出来的 GPU p50 是 7.01 / 3.30，只算忙帧是 6.99 / 3.27，差 0.02–0.03ms。
被冷帧污染的是**尾部**（p95 与那 9 帧超预算的），不是中位——
所以"贵一倍"这个说法本来就不依赖那 9 帧，订正之后它反而更硬了。

### 决策 9 的订正：那 9 帧没有一帧在转场动画中途，而 `framestats` 只给了最后 120 帧

两条方法论问题，都是把原始 dump 重新逐帧过一遍才发现的。工具收进了
[`scripts/analyze-framestats.ps1`](../../../scripts/analyze-framestats.ps1)
（只读文件、不碰设备，历史采集可直接复分析）。

**① `framestats` 的表只保留最后 120 帧，而 `Janky frames` 的分母是整个场景。**
播放页那次 `Total frames rendered: 654`、`Janky frames: 37（5.66%）`，
但表里只有 120 行——也就是**整个场景最后约 1 秒**。上面那张逐帧 CPU/GPU 拆分的表
读的是这 120 行，而 5.66% 读的是 654 帧，两者不是同一个集合。
对照实验本身（Player 5.66% vs Detail 2.23% vs Tab 1.92%）仍然作数：三个数都是
场景级、同一套点击协议、同一口径。不作数的是"那 9 帧说明了转场为什么慢"。

**② 超 16.67ms 的 9 帧，全部是"冷了一段之后画的第一帧"，没有一帧落在连续渲染段内部。**
按前帧 `IntendedVsync` 间隔把帧分成两类（间隔 < 50ms = 连续渲染中；≥ 50ms = 中间冷了）：

| 采集 | 忙帧 | 忙帧超 16.67ms | 冷帧 | 冷帧超 16.67ms | 忙帧成本最大 |
| --- | --- | --- | --- | --- | --- |
| 播放页转场（Player） | 109 | **0** | 11 | **9** | 15.13ms |
| 详情转场（Detail） | 116 | 0 | 4 | 1 | 15.15ms |
| Tab 切换（A） | 114 | 0 | 6 | 0 | 12.40ms |
| 广场滚动（B） | 119 | 0 | 1 | 0 | 6.78ms |

**"冷帧"不等于"没有动画在跑的帧"，这一点必须先说清，否则这条订正会被读歪。**
"转场中途"和"转场首帧"是两件事：中途 = 连续渲染段内部，那里 0 帧超预算，所以
"转场动画在 120Hz 下一次跳两三个 vsync"这个说法确实站不住；
但**转场的第一帧本来就属于转场**，它天然就是"冷了一段之后画的第一帧"。
按"这一帧之后是否紧跟连续帧"再分一次，播放页那 9 帧是：

| 帧号 | 前帧间隔 | 成本 | 其后连续帧数 | 读法 |
| --- | --- | --- | --- | --- |
| 0 | —（窗口首帧） | 17.34 | **47** | **形状上像一次转场的第一帧**，且慢在 CPU（14.48ms）不是 GPU |
| 48 / 112 | 199.5 | 19.51 / 19.24 | 2 | 短段头，GPU 13–14ms |
| 51 | 290.4 | 22.23 | 0 | 孤立 |
| 115–119 | 498.6 / 498.7 / 498.6 / 515.4 / 498.7 | 19.6–21.3 | 0 | 5 帧 500ms 节拍，孤立 |

所以订正的准确表述是：**这 9 帧里没有一帧是"动画正在跑却画不完"**，
其中 6 帧是孤立帧（5 帧 500ms 节拍 + 51 号那一帧）、2 帧是短段头（48 / 112 号）、
1 帧是采集窗口的第一帧（0 号，唯一一帧 CPU 重的，而 CPU 重恰恰是转场首帧该有的形状）。
**不能把冷帧整类排除**——那等于把转场首帧也排除了。

**这条为什么仍然必须改**：原文写的是"那 9/120 帧墙钟超过 16.67ms，也就是在 120Hz 下
一次跳两到三个 vsync"，那是把 9 帧当成同一类、并且默认它们都在转场动画里。
实际它们分属三类，而**唯一可能属于转场的那一帧慢在 CPU**，
与那一段用来支撑结论的 `BlurBackdrop`（GPU 侧）不是同一回事。
`BlurBackdrop` 的账要靠忙帧 GPU 中位与 120Hz 预算那一组数去记，不能靠这 9 帧。

**那 5 帧 500ms 节拍的帧没有归因，不要当结论用**。观察到的只有：播放页那次采集里
有 6 帧是"冷约 500ms 之后画的"（帧号 52、115、116、117、118、119，前帧间隔
499.7 / 498.6 / 498.7 / 498.6 / 515.4 / 498.7ms）——全应用唯一的 500ms 周期源是
`ui/player/PlayerViewModel.kt:239` 的 `POLL_MS = 500L`（播放位置轮询）。
其中 52 号只花 7.55ms（正常），115–119 这 5 帧各花 19.6–21.3ms、GPU 段 18.0–19.6ms。
另外 3 帧超预算的（48、51、112 号）前帧间隔是 199 / 290 / 200ms，不在 500ms 节拍上；
第 0 号那帧是采集窗口的第一帧，成本 17.34ms 但 GPU 只占 2.86ms（CPU 段 14.48ms）。
**9 帧超预算的构成就是：5 帧 500ms 节拍 + 3 帧 200ms 级间隔 + 1 帧窗口首帧，没有一帧在转场中途。**

> 这张表是 `scripts/analyze-framestats.ps1` 之外临时写的
> `build/ps/coldlist.ps1` 出的（列：帧号 / 前帧间隔 / 墙钟成本 / GPU 段）。
> 它是一次性取证，没收进 `scripts/`，因为分桶已经由 `analyze-framestats.ps1` 覆盖，
> 这里只是要看逐帧明细。

但**归因不成立的两条理由**：① 脚本这一段最后一步点的是"返回"，采集时应用停在**首页**，
轮询虽然还在跑（迷你条 `ui/LyraApp.kt:501` 读的是同一个 `uiState`），
歌词面板已经不在树上；② 这 5 帧的 GPU 段有 18–19.6ms，而迷你条那 44dp 封面重绘
不该值这么多。所以要么还有一条没找到的路径在重绘，要么这 5 帧是别的东西。
**要判它得在真机上做一次**：停在首页、播一首歌、静置 10 秒，看 `gfxinfo` 的帧数
是不是每 500ms 涨一帧。涨 → 迷你条确实在跟着轮询重绘，那 `v0.9.2` 记的
"静止时一帧都不画"这条代理量前提**只在没放歌时成立**，
`measure-transition-duration.ps1` 的数帧法在播放中会被污染；不涨 → 这 5 帧另有来源。

补一条**源码层面已经成立**的事实，它让这个待判项有了具体形状：
`PlayerViewModel.syncFromPlayer` 每 500ms 做一次 `_uiState.update { copy(positionMs = …) }`
（`PlayerViewModel.kt:116`），而 `MiniPlayerBar` 用
`viewModel.uiState.collectAsStateWithLifecycle()`（`LyraApp.kt:501`）拿的是**整个** state 对象——
所以只要歌在播，迷你条每 500ms **必然重组一次**，尽管它只读 `song` / `artwork` / `isPlaying`
三个字段。重组不等于重绘（绘制期读的字段没变就不该画），但这一环确实存在，
是"每 500ms 涨一帧"最现成的候选机制。
要收它也是标准做法：把三个字段各用 `map` / `distinctUntilChanged` 取出来，
或者把迷你条拆成只收所需字段的子组合。**本版不做**——它不影响任何用户可见观感，
而这条采集里那 5 帧只说明它至多影响"播放中静置时的帧数"，
而那正是数帧法（量动画时长）会踩到的地方。

**但 `BlurBackdrop` 那笔债没有翻案**（证据已换成上面那条忙帧口径）。这里再补一句它
**为什么在旧口径下一直没显形**：忙帧最贵只到 15.13ms，没超 16.67ms 那一档，
所以按"60Hz 稳态"判它是 0%；换到 120Hz 一档 8.33ms 的预算判就是 45.9%。
**同一个页面、同一批帧，两个口径给出完全相反的结论**——这就是为什么下面「未完成」
第一条把它记成**口径问题**，而不只是 `BlurBackdrop` 问题。

> 顺带一条没能复现的东西：平台那个 `Janky frames` 的**逐帧谓词**对不上。
> 试过 `DisplayPresentTime > FrameDeadline`（114/120 帧，明显不对）、
> `> IntendedVsync + 一档`、`FrameCompleted > FrameDeadline`（本例 9 帧）等几种，
> 没有一个能同时凑出四份采集各自报的数（13 / 19 / 37 / 15）。
> 所以 `analyze-framestats.ps1` **不冒充平台口径**，只报自己的两个口径
> （墙钟成本超预算、`FrameCompleted > FrameDeadline`），平台那个百分数单列一栏供对照。

### 为什么本版不修 `BlurBackdrop`

试过一版"图层只做 1/4 边长、再放大画出去"（高斯模糊与缩放可交换，观感应当不变，
被处理的像素降到约 1/16），编译通过，补丁留在 `build/blur-backdrop-candidate.patch`。
**没有采用**，两个理由：

1. **收益没量到**。改完之后手机掉出 adb，模拟器又进不去播放页（见下），
   GPU p50 从 7.01 降到多少**一个数都没有**。没有数的性能改动不进版本。
2. **观感没量到**。放大带来的双线性插值在 26dp 模糊之上应当看不出来，
   但"应当"不等于"看过"。这条改动动的正是 ADR-0005 明确保护的那层背景。

顺带纠正一处说法，并说明本轮的取证边界：本轮**没能**在模拟器上进到播放页，
因此播放页相关的两项（`BlurBackdrop` 的观感、013 的落点）在模拟器上**判不了**。

现象是迷你条一直显示"未在播放 / 导入音源后即可播放"，点榜单里的歌也不起播。
**成因没有查实**，但有一条现成的嫌疑：为了换签名（旧包是 debug 签名、
新包是 release 签名，`install -r` 报 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`），
本轮先 `uninstall` 再装，**把应用数据一起清了**，导入过的音源因此没了。

这不构成对上面"订正"一节的推翻——那一轮"酷我源在模拟器上能出地址、能播、能出封面"
是实际量过的（播了四首、拿到中韩对照歌词）。两轮都真实发生过，差别大概率就在
**音源是否已导入**这一件事上。结论：**模拟器能不能播取决于有没有音源，
不要把"模拟器一定能播"当成可依赖的前提**，用之前先确认迷你条不是空态。

### 这一轮欠的几件事

- `BlurBackdrop` 的降采样候选：要么在真机上量到 GPU 侧确实下降、且观感无变化再进，
  要么明确记成"播放页转场的已知成本"，不再当共享元素的账。
- 013 的惯性幅度只有方向是干净的（3/3 同向），数值区间没有统计意义：
  `input swipe` 无法控制释放速度。要量幅度得改用 `sendevent` 或注入 MotionEvent。
  （这一条与下面两条都是「决策 9 的订正」之后新增或改写的。）

- **播放中静置时到底画不画帧**（真机，5 分钟）：停在首页、播一首歌、静置 10 秒，
  看 `gfxinfo` 的 `Total frames rendered` 是不是每 500ms 涨一帧。
  这条决定 `v0.9.2` 那条"静止时一帧都不画"的代理量前提要不要加限定，
  也决定那 5 帧的归因。
- **转场口径要不要从"60Hz 稳态"改成 120Hz 一档**：现在的口径下播放页忙帧超预算 0%，
  换成 8.33ms 预算是 45.9%。改口径是**收紧**，不是放宽，但它会让 `BlurBackdrop`
  从"看不见"变成"必须处理"，所以这个决定要单独做、并且记进 CHANGELOG，
  不能在某次顺手改脚本时悄悄发生。
