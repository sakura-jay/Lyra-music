# 歌单 / 榜单卡片 ↔ 详情页头封面共享

**Blocked by**: 010（共享元素的第一处落点）

011 是 [`ADR-0010`](../../../adr/0010-共享元素转场.md) 方案 A 的第二处落点，也是把 010 那套
"两个固定端点"的设施**泛化成任意多处**的那一片：卡片有六个调用点、详情页有四条路由。

## 目标

从哪张卡片点进去，那张卡片上的封面就飞到详情页头的 96dp 大图上；返回时飞回**它来路上那一张**。
路由转场（详情页右侧进入的 280/240 一族）一个数都不动，时长仍走 large 档 350 进 / 450 出 ×
`LocalMotionScale`。

参与的四条路由（页头封面就是这一页自己的封面）：专辑、平台歌单、榜单详情、自建歌单。
**刻意不接**的：`LibraryScreen` 的入口卡（页头是"第一首曲目的图"这种代理，飞过去就是飞错东西）、
我喜欢与本地音乐（同上）、我的歌单的行（没有封面）、搜索结果分组头、`MyPlaylistsScreen`。

## 键怎么定（这一片真正的设计）

1. **卡片端键 = (来源页, 目的地路径)**。来源页不是多余的谨慎：同一个歌单会同时出现在首页推荐排
   与歌单广场（两处都是 `provider.recommended`），同一个榜同时出现在首页预览与榜单广场。只按目的地
   分键的话，"从首页点进去、退回首页"可能飞到广场那张卡的**旧**坐标上，而广场此刻根本不在栈里。
2. **用路径当键，不用封面 URL 当键**。同一条列表的卡片与页头可能各自拿到不同尺寸的地址
   （酷我的推荐列表给 `img`、歌单详情给 `pic`），按 URL 判同会把该飞的判成不飞；
   按路径判还天然排除"A 的封面飞进 B 的页头"。
3. **两端各自从同一批 `LyraRoutes` builder 推导键**，中间没有一个 id 从卡片传到页面。
   这是 `coverPath()` 必须同时被注册处（`detailPathOf`）与页面侧用的原因——白名单只有一份。
4. `#` 不出现在任何路由里，所以固定端点（`MINI` / `PLAYER`）与路径键不可能撞车。

## 四条刻意的取舍（含性能）

1. **登记表是普通 `HashMap`，不是快照状态**。端点靠 `onGloballyPositioned` 报矩形，而列表滚动时
   每个可见项**每一帧**都在报。这张表若 observable，写入会失效所有读它的组合节点，于是
   "滚一格 = 整页重组"，正撞 `v0.9.2` 定下的滚动 Jank 门槛（< 1%）。表只在飞行开始那一刻被读，
   飞行期间的实时矩形由覆盖层在绘制里现量——组合期一处都不读它，所以它不需要被观察。
   只有 `landing` 是 `mutableStateOf`（飞行期间才非空，只有覆盖层订阅）。
2. **端点隐身用 lambda 版 `graphicsLayer { alpha = … }`**，不是 `Modifier.alpha(value)`。
   后者写法一样能动，但那是**组合期**读飞行状态：一次起飞会让整页的卡各重组一遍，
   而那正好压在转场首帧的预算上（工单 001 量的就是这个）。
3. **终点矩形现量**（`Entry.rectNow()` 优先读 `LayoutCoordinates`，detach 了才退回快照）。
   原因：路由转场只改 `graphicsLayer`，placement 不会重测——只靠回调会把终点量成"滑到位之后"
   的位置，封面会提前贴上去。这一条不是推理，`CoverAnchorTracksLayerTranslationTest` 用
   祖先图层 `translationY` 把它钉住了（回调是否重跑 + 稍后读坐标是否含位移，各一条）。
4. **鬼影飞行不许发生**：往回飞时若落点键从未登记（例如从专辑页退回歌单页——进专辑页的入口
   本来不是封面卡片），`begin()` 拒绝起飞。否则表现是"页头封面在原地淡一下"，无意义。
   进场反过来允许落点暂时为空：目标页正在进来，覆盖层第一帧停在起点、随后跟上它的实时矩形。

## 撤掉 010 的那层补报（重要，别再写回来）

010 里写过 `CoverFlightState.refreshArtwork()` + 一个 `SideEffect`，理由是"换曲时封面换了图但
布局没变，`onGloballyPositioned` 不会重跑，登记表会留着上一首歌的位图"。

**这个理由是错的，实测证伪**：把 `SideEffect` 注释掉之后，7 条 `CoverDetailFlightUiTest` 全过，
包括专门测换图的那条 `aCardWhoseCoverWasSwappedFliesTheNewCover`。真正发生的是：那行 modifier 读的
`artwork` 是本次重组捕获的值，捕获一变挂上去的就是**新的 lambda 节点**，Compose 会重跑 placement。
所以 `onGloballyPositioned` 是登记表唯一的写入点，补报、`snapshot.copy` 那条路径一起删掉。
判据留在测试的 KDoc 里，防的是有人按直觉把它加回来。

## 一个必须记住的 API 坑

取路由参数用 `arguments?.get(name)?.toString()`，**不是 `getString(name)`**：自建歌单的 id 声明成
`navArgument` 的 `defaultValue = 0`（Int），`getString` 对 Int 只返回 null——那一页永远不飞，
而且不崩、看不出来。同理 `coverPath()` 里 `my-playlist/0` 与非数字 id 都判成"还没拿到参数"。

  原先这里写过一句"因为缓动前段快、看得见的那段本来就短"，**那是编的**：
  尾段 24px 在录像里逐帧看得见（20→16→12→10→8→6→4→2→0），
  不存在"小于步长所以看不见"。真正可能的原因有三条，都没验：

  ③ 点击到动画真正起跑之间的组合延迟没有计入。

  但那条法子在播放中会被 500ms 轮询污染（见 `../../v0.9.2/CHANGELOG.md` 的口径订正），
  所以得先把播放停下来再量。**这条记在「未完成」里。**
