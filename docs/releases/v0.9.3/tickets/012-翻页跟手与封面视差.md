# 播放页翻页跟手与封面视差

**Blocked by**: 006（页码指示器）、010（共享元素）

**主交互**：无匹配模式 · 延续 006 的 Expanding Tag Selection（模式 10）——改的是**驱动源**，不是交互语义

## 目标

播放页左右翻页时，页码指示器不再"翻完才跳"，而是**手指拖到哪，药丸就长到哪**；封面再加一层
小幅落后的视差。006 明确写着"`currentPageOffsetFraction` 本版不接，留给 M10（012）"，本片把那句话兑现。

  也因为它现在得被设备测试直接驱动。签名多了 `position: () -> Float`。
- [x] `PlayerScreen.kt`：页宽用 `onSizeChanged` 量一次喂给视差；视差**只挂封面**那一层，

## 三条设计判断

### 1. 几何跟手，身份跳变（本片唯一一处观感上的取舍）

宽度与让位每帧从连续位置现算，**颜色仍由离散的 `currentPage` 驱动**。理由：几何回答的是
"这块图现在有多像当前页"，这是个连续量；颜色回答的是"哪一页是当前页"，这是身份。
半程时把两枚都染成中间色，读起来是"这两页都是当前页"，那不是信息。

顺带一个容易写错的地方：`current` 与 `position` 是**两个来源**——一个组合期读、一个绘制期读。
合成一个不行：只给离散值退回 006 的"翻完才跳"，只给连续值则每一帧重组那一行。

### 2. 偏移量只在**绘制期**读

`rememberPagerPosition` 返回的是 `() -> Float` 而不是 `Float`，`PageIndicator` 收的也是
`() -> Float`。这不是风格：`currentPageOffsetFraction` 是每帧变的快照状态，组合期读它会让
拖动的每一帧重组指示器那一行与封面那一摞——而翻页正压在 v0.9.2 定下的"滚动 + 转场首帧"
那两个 Jank 场景上。

这条**有测试钉住**（`PagerFollowUiTest` 数重组：80 帧拖动计数为 0，最后再量一次像素证明
"没重组"不等于"什么都没画"），而且配了一条反面用例：把读法改成组合期，计数器必须涨。
没有反面用例的话，"计数为 0"完全可能是"计数器本身坏了"。

### 3. 视差只给封面，不给歌词页

歌词页唯一要读的就是字。文字以一个与页面不同的速度漂，读到的是"字在晃"，不是深度。
整页一起位移也没有意义：`verticalScroll` 的可视高度不变，用户看到的还是"一整页在动"。

**为什么是落后而不是超前**：落后读成"封面在玻璃后面"，那是深度；超前读成"这块图被甩出去了"，
而且会把它推向页面边界。

## 视差量是多少、怎么定的

`PARALLAX_RATIO = 0.08f`，定义是**页宽的百分比**而不是写死 dp——写死 20dp 的话折叠屏展开或
横屏后页宽变了而视差没变，深度感跟着屏幕尺寸一起失真。

PLAN §012 原文写"具体数值在真机上定"，**实际没有靠真机定**，这个数是被两条已有的界夹出来的：
- 上界是布局给的横向余量：封面 230dp、页边距 20dp，两侧余量各约 45dp；视差最大的一瞬是
  `position` 走到相邻整数那一步，`ratio × 页宽 ≈ 0.08 × 360dp ≈ 29dp`，仍小于 45dp，
  所以封面不会被推出自己的可视范围；中点（最容易被盯着看的那一帧）约 14dp。
- JVM 的 `parallaxStaysSmallEnoughToReadAsDepth` 把它夹在页宽 5%–12%（满程）与 ≤ 8%（中点），
  **常数以后被改大会先响**，而不是等真机上看见"封面在飞"。

所以真机目视剩下来的任务是"好不好看"，不是"选一个数"。

## 验收标准

- `PagerFollowUiTest` 9 条：一帧之内的宽度等于算术值（这条把"跟手"与"弹簧追离散目标"分开，
  后者在端点与中点上给出同样的值、能通过全部 JVM 测试）、中途反向立刻回到那一档、
  行布局矩形一动不动（ADR-0009 护栏二）、颜色不许半程、视差静止为 0 / 中点等于页宽 4% /
  回到原点（期望像素**手写**成 `600 × 0.08 × 0.5 = 24px`，不从常数算）、
  真 `pagerState` 停在半页时指示器真的半程、缩放置 0 时 snap、
  以及上面那两条重组计数（80 帧拖动计数为 0 / 组合期读法计数必须涨）。
- `PagerMotionTest` 10 条，其中 `dotGapIsConstantThroughTheDrag` 证的是拖动全程两颗点之间的
  **视觉间距恒等于 6dp**（= 布局上那个 `spacedBy(6.dp)`）：宽度在变、让位也在变，两个都在动的量
  凑出一个不变的间距，才是"看不出两个东西在分别动"。这是 006"邻居不重叠、不跳位"的推广。
- 变异测试验过两套断言都不是自指的：把 `follow` 判据与 `PARALLAX_RATIO` 分别改坏，
  JVM 响 2 条、设备响 1 条。**第一版里视差那条的期望值是从常数算出来的，等于没断言**，
  已改成写死 `600 × 0.08 × 0.5 = 24px`。
- 路由转场、010/011 的共享元素、006 的弹簧常数：一个数都没动。
- **真机录屏已补一部分**（PLK110 release，`build/walk/pager.mp4`，
  逐帧拼图 `build/walk/sheet/pager_seq.png`）：一次 400ms 的 `input swipe`
  被抽到约 20 帧，**翻页本身连续可见**（封面、歌名、音质标签、进度条一起滑过去）。
  **但"视差"这一半，录像判不了，本轮没判成。**
  原先这里写的是"封面比页面慢看得见"，那是目视拼图得出的，站不住：
  视差量是页宽的约 4%（`PARALLAX_RATIO` 的一半在中点），一页 1272px 下约 50px，
  肉眼在缩略拼图里分不出"少滑 50px"和"一起滑"。
  本轮试过用列亮度探针
  （`build/ps/parallax.ps1`，取 y 500–900 那条带）去数封面中心的横向位移，
  结果从 288.5px 只挪到 286.5px——**那个探针测错了对象**：
  播放页那一层 `BlurBackdrop` 是贴在屏幕上的、不随页面滑动，
  这条带里最暗的东西被它主导了。要量得改取封面自身那块矩形的列剖面，
  而那是另一件事，本片没做。**结论：视差的量只由像素测试负责，录像只负责"翻页顺不顺"。**
  **跟手那一半仍然没有、也不能靠录像判**：录像的帧时间戳与手指位置对不上，
  判不了"这一帧页面应该停在拖动的百分之几"。所以"药丸跟着手指"这一项
  的判据仍然是下面那两套像素测试（`dotGapIsConstantThroughTheDrag` 等），
  本片原本写的判据分工没变。**这里原本的理由是"`screenrecord` 每帧字节相同"，**那句是错的**：
  后来量出来是**帧率**问题——一段 4 秒录像只有 5 帧（约 1.4fps），静止画面才字节相同，
  动画照样被抽到（一次 280ms 的路由转场就被抓到过一帧两页同屏的中间态）。
  手机自己的 `screenrecord` 动画期约 119fps（这一段实测约 20 帧 / 400ms），
  所以"看得见在动"这一项真机判得了，"动得对不对"仍然只有像素测试判得了。
  本片的翻页是**跟手**的，`input swipe` 那 400ms 里手指在动、页面也在动，
  抽到的那一帧不代表"拖到一半"，所以判据仍然只能是像素测试。
  完整订正见 [`../CHANGELOG.md`](../CHANGELOG.md) 的"订正：这一轮量下来，模拟器比文档里写的能用"。
