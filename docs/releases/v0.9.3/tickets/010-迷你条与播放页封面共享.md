# 迷你播放条 ↔ 播放页封面共享

**Blocked by**: 009（动效地基）

**共享元素在本项目的第一个落点**（[ADR-0010](../../../adr/0010-共享元素转场.md) 的方案 A）。

## 目标

从哪张封面点的，封面就飞到哪去：迷你播放条上那块 44dp 的封面，点开后变成播放页里 230dp
的大图；返回时飞回去。路由转场（播放页 280 入 / 240 出 + 既有 spring）一个数都不动。

## 涉及层

- [x] `ui/common/CoverFlight.kt`：
  - `coverFlightRect` / `coverFlightCorner` / `coverCropSource` 三个纯函数（JVM 单测覆盖）；
  - `CoverFlightState`：两端把"我现在在哪、圆角多大、图是哪张"报进来，触发时取起点快照
    与终点实时矩形；
  - `CoverFlightOverlay`：整屏 `Canvas`，画在 `Scaffold` 之上、`NavHost` 之外。
- [x] `LyraApp`：路由一变就起一次飞行（进播放页 / 离开播放页）。挂在路由变化上而不是点击回调上，
  按钮返回、手势返回、系统返回因此走同一条路。
- [x] `PlayerScreen` / `MiniPlayerBar`：封面容器接 `Modifier.lyraCoverAnchor(...)`，
  飞行期间原地那一份隐身（保留在树上，否则量不到矩形）。
- [x] `CoverFlightTest`：8 条纯函数断言（两端精确、线性、夹紧、Crop 裁法、退化尺寸）。
- [x] `CoverFlightUiTest`：2 条**像素**断言（模拟器上跑，不需要真音源）。覆盖层是整屏
  `Canvas`，语义树里既没有节点也没有属性，`gfxinfo` 又只看得到掉不掉帧，所以这一段的
  位置只能靠"哪块像素是封面色"反推：自造一张纯色封面，后飞行的外接矩形必须严格落在
  两个端点之间、两端自己那一份必须隐身、落位后两端必须画回来、缩放置 0 时整件事不发生。

## 三条刻意的取舍

1. **不插值布局**：位置 / 尺寸 / 圆角只体现在绘制参数上，没有任何一帧改 `size()`
   ——ADR-0009 护栏二（尺寸一动画，周围的东西全在动）。
2. **起点是快照、终点读实时**：进播放页时迷你条在同一次重组里就从树上消失，起点只能是消失前
   量到的那一份；播放页自己还在路由转场里滑，终点跟着它走才不会"两套位移打架"。
3. **图没到就不飞**：`artwork == null` 时整件事不发生，行为退化成硬切——插值一张占位图更糟。

## 与 ADR-0010 的差异（不是退路 B）

ADR 写的是"用 `androidx.compose.animation` 里的共享元素设施"。落地的实现是**同一个设计**
（覆盖层 + 两端登记 + 位置/尺寸/圆角插值），但没有用 `SharedTransitionLayout`：

- 那套设施的前提是两端在同一次动画里同时可见（`AnimatedVisibility` 或导航的
  `AnimatedContentScope`）；
- 本项目的迷你条是 `Scaffold.bottomBar` 里的 `if (currentRoute != PLAYER)`——进播放页时
  它和播放页不是"一次转场里的两个状态"，硬接进那套 API 只会得到"从目标位置淡入"的半截效果；
- 覆盖层方案同样满足 ADR 的三条硬约束：跨导航存活、图到才插值、圆角一起插值。

时长仍走 large 档（350 进 / 450 出）× `LocalMotionScale`；缩放置 0 时整件事不发生，
当帧到位。

## 验收标准

- **真机录屏**（PLK110）：进 / 出播放页各一段，中间帧必须看得到封面在飞。
  ~~模拟器上没有可播放的音源，拿不到带封面的迷你条，所以这条只能在真机上做。~~
  **这句是错的，已按实测订正**：模拟器上酷我音源可用，迷你条有真封面，来回六趟录到了飞行中间帧
  （`build/walk/f010b.mp4`，逐帧在 `build/walk/f010b/`，拼图 `build/walk/sheet/f010b_big.png`）。
  但模拟器的 `screenrecord` 是变码率，13 秒只给 46 帧（约 2.8 有效 fps，卡顿期间更低），
  所以模拟器能证"确实在飞"，证不了"飞得顺"——真机录屏这一条仍然要补，只是理由换成了后者。
  **真机这一段已补**（PLK110 release，`build/walk/flight.mp4` / `flight2.mp4`）：
  封面从迷你条左下飞到播放页大图位，连续变大、圆角同步插值；
  **跨 324ms 那个数本轮订正为不成立**：它就是我挑的 f0029–f0068 这段帧区间的跨度
  （`ffprobe` 真实时间戳 4.178 → 4.503 = 324.3ms），**不是**逐帧定起止定出来的——
  与 014 那句"约 116ms"是同一个循环论证，一并作废。
  **重测口径**：逐帧差分，区域 = 封面位 + 其下方文字带（`x 140..1130, y 180..960`），
  判据 = 单像素 RGB 三通道差之和 > 60 且单行 > 3 个像素。结果：变化从 f0030（t=4.188）
  起、到 f0072（t=4.537）止，两侧 f0029 与 f0073 零变化。于是这一段**可见变化跨 349ms**
  （真值夹在 (4.178, 4.544] = 366ms 之内），与规格 large 档进入 350ms 一致。
  **但这个数量的是什么要说清**：那块区域里同时有三样东西在动——路由位移（280ms）、
  封面飞行（350ms）、`BlurBackdrop` 背景交叉淡出（450ms，ADR-0005）。所以 349ms 是
  **整段转场**的变化窗口，对封面飞行而言只是**上界**；把飞行从另两样里单独剥出来
  **本轮没做**（要沿飞行路径逐帧定位封面，即 011 那套 `covertrace` 的口径）。
  同一段录像里 f0003–f0012 还有一次更短的变化（约 150ms），**没有判据说明它是哪一趟**
  ——`flight.mp4` 与 `flight2.mp4` 各自对应进还是出，本轮没有重新确认，故不写结论。
  手机录像动画期中位 8.4ms/帧（≈119fps），"顺不顺"这一项判得了。
  数与判据强度见 [`../CHANGELOG.md`](../CHANGELOG.md)「真机验收」表。
- 模拟器上的 `CoverFlightUiTest` 已绿：它证的是"覆盖层确实在中间画了、两端确实让开了"，
  真机录屏证的是"真封面飞起来好不好看"——两件不同的事，不能互相替代。
- JVM 单测覆盖三个纯函数；`:app:lintDebug` 0 error；既有 instrumented 全量不掉。
- reduced-motion（系统动画缩放 0）下当帧到位，不出现半截封面。
