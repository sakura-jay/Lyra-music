- 首页两排、榜单详情头脚、搜索分组按 40ms 依次出现（总上限 240ms）。
- 换配色时新主色从色板点击点扩散一圈（纯反馈覆盖层，真实配色当帧就生效）。

## 决策 1：动效缩放必须除掉平台那一份（双重缩放）

`ADR-0009` 把"平台可能已经自己乘过一次"列为**已知风险**，并写明落点是
`MotionSpec.durationMsOf` 一处。本版把它量实了，并修掉。

**证据（字节码 + 实测）**

- 反编译 `androidx.compose.animation:animation-core` 1.11.4：
  `SuspendAnimationKt.doAnimationFrameWithScale` 里
  `playTimeNanos = if (durationScale == 0f) anim.durationNanos else (frameTimeNanos - startTimeNanos) / durationScale`，
  而 `durationScale = coroutineContext[MotionDurationScale]?.scaleFactor ?: 1f`。
  这是 **tween 与 spring 共用**的那条帧循环，所以两类动画都会被缩放。
- 反编译 `androidx.compose.ui:ui` 1.11.4：`WindowRecomposer_androidKt.getAnimationScaleFlowFor`
  读 `Settings.Global.animator_duration_scale` 并注册 `ContentObserver`，喂给
  `MotionDurationScaleImpl`。也就是说**平台确实乘过**。
- 实测（Pixel_8 模拟器上跑真应用窗口，同一动作"切页后持续渲染时长"，各 3 次）：
  `animator_duration_scale` 1.0 → 980 / 963 / 928ms，2.0 → 1787 / 1751 / 1738ms。
  我们的 `clamp` 在 2.0 时**必然**输出 1.0（夹紧上限），所以那 ~1.85 倍只可能来自平台——
  正是"不放大"这条表态被反着执行。

  为什么这条**可以**用模拟器量：它量的是"改一个系统设置，动画墙钟怎么变"，走的是真应用的
  真窗口 recomposer，与真机是同一条链；仪器测试量不到是因为测试框架自带 recomposer 与时钟。
  反过来，**jank 的绝对值仍然只认真机**（模拟器 60Hz、无真机 GPU），下面那两张表的数都来自 PLK110。

**改法**

`LocalMotionScale` 的语义从"用户想要的倍率"改成"**该写进 spec 的乘数**"：

```kotlin
multiplier = clamp(animator, transition) / platformFactor(animator)   // 即 intent / animator
```

除掉再让平台乘回来，墙钟时长恰好等于 `基准 × intent`。弹簧没有时长可乘，用等价的刚度换算
`stiffness ×= 1 / multiplier²`（周期 ∝ `1/√stiffness`），与 tween 走同一个等式。

平台真正缺的只有两件事，而这两件才是本层要补的：**它只读 animator 一档**
（`transition_animation_scale` 完全不理）、**它不夹紧上限**。

**默认档零风险**：`animator = 1.0` 时 `multiplier = 1.0`、刚度倍率 = 1，
所有动画与本次改动之前**一字不差**。只有用户动过系统缩放才有差别。

**改后复测（同一隔离场景：音乐库 → 我喜欢，只有一条路由转场在动，1400ms 窗口内数帧）**

| `animator` | 想要的倍率 | 乘进 spec 的数 | 预测墙钟 | 实测帧数（4 次） |
| --- | --- | --- | --- | --- |
| 1.0 | 1.0 | 1.0 | 1.0× | 42 / 43 / 44 / 43 |
| **2.0** | 1.0（夹住） | **0.5** | 0.5 × 2.0 = **1.0×** | **44 / 40 / 43 / 44** |
| **0.5** | 0.5 | 1.0 | **0.5×** | **25 / 22 / 24 / 25** |
| 1.0（回到起点复量） | 1.0 | 1.0 | 1.0× | 41 / 44 / 44 / 43 |

三档全部落在预测上：`2.0` 与 `1.0` **完全一样**（改之前是 1.85 倍长），`0.5` 是半速
（24 ≈ 43/2，多出的两三帧是点击与首帧的固定开销）。

这条复测必须在**真应用窗口**上做，不能在仪器测试里做：只有真窗口的 recomposer 才带着
平台的 `MotionDurationScale`。数帧之所以够用，是因为静止时应用一帧都不画。

**已知残余**：`animateItem()` 内部那两条 spring 由 foundation 自己构造，我们改不到刚度，
所以它在 `animator = 2.0` 时仍会被平台放大到 2 倍。`lyraAnimatedItem` 只保住了
"关掉动画时整条不播"。要根治得给 `animateItem` 传显式 spec，本版不做。

## 决策 2：Jank 门槛按场景拆开，转场首帧改为"60Hz 稳态"口径

工单 001 允许三种结局，实测后走**第 3 种**，理由与数据都在
[`tickets/001-首帧-jank-定位与收口.md`](tickets/001-首帧-jank-定位与收口.md)。这里只记决策本身。

**实测（PLK110，release 包，M9 全部改动、不含 001 的修复）**

| 场景 | 帧数 | Janky（新指标） | legacy | p50/p90/p95/p99 |
| --- | --- | --- | --- | --- |
| A：12 次 Tab 切换 | 675 | **14（2.07%）** | 30（4.44%） | 5 / 7 / 9 / 21 ms |
| B：榜单广场连甩 24 次 | 865 | **0（0.00%）** | 0（0.00%） | 5 / 5 / 5 / 6 ms |

滚动这一半的 <1% **本来就达标**，而且是零帧。转场这一半 2.07%。

**为什么判定"120Hz 转场首帧不可达标"，而不是继续找代码的锅**

逐帧拆 `framestats`：正常帧墙钟 4.71ms，其中 UI 线程在 `PerformTraversalsStart → DrawStart`
之间只花 **~1ms**。慢帧的两种签名都不在遍历期里：

1. `PerformTraversalsStart - IntendedVsync` = 4–9.4ms —— 帧**起跑就晚**，预算在开工前已被吃掉；
2. `FrameCompleted - SwapBuffers` = 8.4–11.8ms —— 画完提交了，合成侧滑过一个 vsync。

允许结局里的 ①「抑制转场期间的重组」和 ②「内容延迟订阅」治的都是"首帧太重"。
而首帧不重（1ms），所以两条都无从下手。**①已经在模拟器上用对照组证伪**：
有错峰揭示的首页与没有的音乐库，700 / 1500 / 3000ms 三个窗口下帧数完全一样。

**新门槛**

- 列表/广场滚动：`Janky frames < 1%`（维持，已达标）。
- 转场：`60Hz 稳态 < 1%` **且** 不掉出 120Hz（帧间隔 p50 8.31ms 即视为稳住 120Hz）。

**重新收紧的条件**（任一成立就回来重量）：① 换图片库或改封面解码路径；
② M10 共享元素转场落地之后；③ 系统侧 vsync / 刷新率策略变化。

> **这一条在 M10 收口时量完了，之后又被推翻两次**，第二次推翻的是本版的**口径**本身。
> 完整数据与逐帧明细在
> [`../v0.9.3/CHANGELOG.md`](../v0.9.3/CHANGELOG.md) 的「真机验收」决策 9 与「决策 9 的订正」，
> 工具是 [`scripts/analyze-framestats.ps1`](../../../scripts/analyze-framestats.ps1)
> （只读文件、不碰设备，历史采集可直接复分析）。这里只记对本版的影响。
>
> **第一次推翻（归因）**：那 5.66% 不是共享元素的成本，是播放页那层全屏 `BlurBackdrop`，
> 而它是 v0.4.0 就有的东西。
>
> **第二次推翻（口径）**，三条，都是把原始 dump 逐帧重过一遍才发现的：
>
> 1. `framestats` 的逐帧表**只保留最后 120 帧**（本文所有采集的表都是 120 行；
>    只有一份总帧数不足 120 的采集给了全部），而 `Janky frames` 的分母是整个场景
>    （本文表里的 675 / 865 / 676 / 853 那些总数）。所以"场景级百分数"和"逐帧拆分"
>    读的根本不是同一批帧，本文当时把两者当同一批用了。
>    **上面那几个百分数仍然作数**（它们是场景级的）。
> 2. 本文引用的那两种慢帧签名，**区间的上端都落在冷帧上**
>    （冷帧 = 前帧间隔 ≥ 50ms，即这一帧之前应用冷了几百毫秒；忙帧 = < 50ms，连续渲染中）。
>    `jank-before-transition.txt` 那 120 行里：
>    `PerformTraversalsStart - IntendedVsync` 忙帧最大 8.50ms、冷帧最大 9.41ms
>    （> 4ms 的：忙 2 帧 / 冷 3 帧）；
>    `FrameCompleted - SwapBuffers` 忙帧最大 9.85ms、冷帧最大 11.80ms
>    （> 8.4ms 的：忙 2 帧 / 冷 2 帧）。
>    也就是"4–9.4"与"8.4–11.8"这两个上界是冷帧给的，写成转场的慢帧签名不准确。
> 3. 冷帧慢是**CPU 段与 GPU 段一起慢**（五份采集一致；均值 ms，
>    CPU = `HandleInputStart → IssueDrawCommandsStart`，GPU = 其后到 `FrameCompleted`）：
>
>    | 采集 | 忙帧 CPU / GPU | 冷帧 CPU / GPU |
>    | --- | --- | --- |
>    | `jank-before-transition` | 1.92 / 2.76 | 5.52 / 5.88 |
>    | `phone001` 转场 | 1.49 / 2.61 | 3.29 / 3.55 |
>    | `phone-probe` X | 1.99 / 3.00 | 5.48 / 6.83 |
>    | `phone-detail` | 1.12 / 3.24 | 4.15 / 7.18 |
>    | `phone-player` | 1.13 / 6.72 | 4.11 / 13.74 |
>
>    **成因没有查实**。这个形状与"冷下来之后再起步时整条链都慢"（DVFS 未回升、缓存冷）相符，
>    但本轮没量过 CPU / GPU 时钟，所以那只是与观察一致的解释。
>    被形状排除的是"应用里有活儿没干完"：那样慢会留在同一类帧上，不会与前帧间隔相关。
>
> **对本版结论的实际影响：方向不变，但有一条要纠正读法。**
>
> - 不变的部分：按 16.67ms 那一档判，**忙帧里超预算的一帧都没有**
>   （`jank-before-transition` 0/114，忙帧最大 11.63ms；M10 四份是 0/109、0/116、0/114、0/119）。
>   "首帧不重（遍历期 ~1ms）"也不依赖冷帧。所以"120Hz 转场首帧不可达标"这个判断**没有被推翻**。
> - 要纠正的读法：**冷帧不能整类排除**。"转场中途"（连续渲染段内部）确实一帧不超，
>   但"转场第一帧"天然就是冷帧——它是转场的一部分，本来就该算。
>   能排的只有"后面没有连续帧的孤立冷帧"。
>   播放页那次 11 帧冷帧里 7 帧是孤立的（含那 5 帧 500ms 节拍，归因未查实），
>   而**唯一一帧 CPU 重的**（窗口第 0 帧：14.48ms CPU / 2.86ms GPU，其后紧跟 47 帧连续渲染）
>   形状上正像一次转场的第一帧，且它慢在 CPU、与 `BlurBackdrop` 无关。
>   单帧样本、未重复，所以不下结论，但它是 M10 新增待量项的第一条。
> - 一个要说清的例外：`build/phone-player-noanim/` 那份（105 帧、`Janky frames: 42（40.00%）`）
>   忙帧也超（3/49，冷帧 24/55）。**没有任何文档记过它是在什么操作条件下采的**，
>   目录名里的 "noanim" 是唯一线索，本轮没有证实也没有证伪那个读法。
>   它不参与上面任何一条结论，记在这里只为免得下次被当成漏掉的证据。
>   **不要拿那个 40% 去改门槛。**
>
> **本版的门槛不因此改动**：滚动那条是场景级数、转场那条按 60Hz 稳态判，两者都还成立。
> 要不要改成按 120Hz 一档（8.33ms）的预算判，是 M10 列出的待决项——
> 那个口径下播放页忙帧超预算 45.9%（详情页 2.6%），所以这是一次**收紧**，
> 不在此静默执行。

## 真机验收补录（PLK110，release 包，三档系统缩放均为 1.0）

装的是**当前代码树现打的 release 包**（`0.9.3` / `versionCode 8`，原地更新、数据保留）。
之前机上那个 0.9.2 是 10-18 19:25 打的，早于 `f18f6e2` 与全部 M10，量它没有意义。

**为什么这一轮能量 micro / small 档**：手机自己的 `screenrecord` 是**可变帧率**，
动画期间中位 8.4ms/帧（≈119fps），比模拟器的 2.8fps 高两个数量级。
上一版"中间帧取不到、只能真机"的判断是对的，但当时没量到是因为设备掉线，不是因为真机也取不到。

| 片 | 量到了什么 | 判据 |
| --- | --- | --- |
| 004 按压 | 卡片宽度 1161→1137px = **0.979**，两侧对称；按下保持、抬起恢复；下 100ms、上 92–120ms | 与规格 0.98 / 100 / 120 一致 |
| 005 ♥ | 220ms 内 15 帧：描边 → 部分填充 → 实心 + 涟漪在后；再点一次可逆 | 首次**看见**而非推断 |
| 006 页码 | 12 帧竖条：药丸收窄 / 圆点变宽连续变化，身份在中点交换，无重叠 | 与"几何连续、身份跳变"一致 |
| 007 让位 | 存活行歌名纵向位移 **156→144→132→116→108→96→84→76→68→60→52→48→40→36→32→28→24→20→16→12→0**（21 个中间值，单调减速、**无过冲**），266ms | 模板匹配（cost 0.5–1.5，次优 ≥19）；NoBouncy 弹簧的形状 |
| 008 Snackbar | 进 116ms / 出 117ms；提示条在场期间列表行**不动**（首页 `dy=0` 连续 84 帧） | material3 自带过渡，非 medium 档 |

**008 的一条订正**：工单里"提示条不参与列表布局"在**首页成立**（量了，`dy=0`），
但榜单详情页那一处**不成立**——提示条在场期间列表整体上移 28px（=8dp），提示条离场后回落。
成因没有定位（同一轮里"点歌开始播放"也会改迷你条状态，两个变量没分开），
所以这里只记**现象**、不记结论。要定位得用一个既不切页也不起播的触发。

2% 上下是这台机器在 120Hz 下的地板，不是我们的开销。当时写"缺了它们就只有帧时间戳、
没有对照组"，缺的正是这一格。

**Perfetto trace 仍然没做**：`perfetto` 采到的东西 `framestats` 已经能给结论，
而 X/Y/Z 三个对照组才是当时真正缺的证据，它先做了。

**顺手修掉的一个假通过**：`measure-motion.ps1` 里**提交进仓库的那个版本**（`088dfe3`，
