# 列表增删让位（lyraAnimatedItem）

**Blocked by**: 002

## 目标

删掉一行 / 一张卡之后，下面那些"瞬间跳上来"改成让位滑动。**模式 8（卡片曲线删除）判定不适用**。

## 涉及层

- [x] `ui/common/LyraAnimatedItem.kt`：`LazyItemScope.lyraAnimatedItem()`。开着动画时用
  `Modifier.animateItem()`；`scale ≤ 0.1` 时三个 spec 全给 `null`（不淡入、不淡出、不让位）。
- [x] 落点（本地数据、key 唯一）：我喜欢（`TrackListScreen`）、我的歌单、收藏的歌单、音源页、
  搜索页的分组。
- [x] 远端搜索结果与榜 / 专辑列表：**只让位、不传 key**（key 不稳的列表用 key 反而会整列重建）。

## 偏差记录：时序与模式 8 相反

模式 8 的做法是"先播动画、再改数据"，因为卡片是飞向一个回收区域的。本项目**没有"删除去向"
的回收区域**（行是直接消失的），所以时序反过来：**数据先删、视觉后收**——
`FavoritesRepository.toggle` 不等待动画，动画只是对已经发生的事实的表达。

## 为什么不能直接用 `animateItem()`

Compose 的 `animateItem()` 用它自己的两条 spring，**不读** `ANIMATOR_DURATION_SCALE`——
直接用它就等于在"别动"的表态下仍然让每一行淡入淡出三百毫秒。弹簧没有时长可乘（与路由转场
同一个问题），所以规则也是二选一：照样播，或者整条不播。

## 验收标准

- ui-test（`rowsSnapIntoPlaceWhenAnimationsAreOff` / `rowsSlideIntoPlaceWhenAnimationsAreOn`）：
  用 `mainClock` 逐帧看**行的位置**——关掉动画时当帧到位，打开动画时两帧后仍在路上。
- 真机目视：55 首的我喜欢页移出中间一首，下面的行滑上来而不是跳。
- **一条实测结论要记住**：被移除那一项的语义节点会在**下一帧**就消失，即使动画开着。
  所以"节点还在不在"判不了这件事，只能判位置——别再用节点存在性写这类断言。
