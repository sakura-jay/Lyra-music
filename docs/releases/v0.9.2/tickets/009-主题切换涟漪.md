# 主题切换涟漪覆盖层

**Blocked by**: 002

**模式 1（Radial Theme Transition）的降级形态**。

## 目标

设置页点色板换配色时，从点击坐标扩散一圈新色的涟漪，把"换了"这件事说出来。

## 涉及层

- [x] `ui/common/ThemeRipple.kt`：`themeRippleRadius(tapX, tapY, w, h)`（点到覆盖层四角的
  **最远距离**，纯函数、可 JVM 单测）、`ThemeRippleState` / `rememberThemeRippleState()`、
  `ThemeRippleOverlay()`。
- [x] `ThemeRippleOverlay`：**始终在树上**的 `Canvas`（不是有涟漪才出现），自己记
  `positionInRoot` 再在绘制时减掉；不吃触摸、不参与测量；`alpha 0.35 → 0`、250ms（medium 档）；
  连点由 `id` 重新起跳，不接在半路的进度上；`scale ≤ 0.1` 时连一圈都不放。
- [x] `SettingsScreen`：色板点击坐标换算成 root 坐标后触发；涟漪色取当前预设的 `primary`
  （明暗由 `surface.luminance()` 判）。

## 为什么不做完整模式 1

真实的径向揭示要**双主题树 + `PixelCopy` 快照裁切**：把旧界面画进位图、按圆裁开、把新界面从
圆心长出来。本项目的主题**只换色不换布局**，快照裁切的收益不抵它在首帧上加的工作量，而且
它会直接跟 001 要收的首帧 jank 抢预算。所以：

- **真实配色在 t = 0 就生效**，涟漪只是覆盖层的视觉反馈，不承担揭示新界面的职责；
- 完整模式 1 列为 M10 的 stretch，前提是 M9 的首帧 jank 已收口。

## 偏差记录

- 覆盖层只铺**设置页那一条路由的矩形**（不是整个 Activity）：用户只可能在这一页点色板，
  给不需要的地方铺一层全屏 `Canvas` 是白付的合成成本。
- 涟漪半径按覆盖层矩形算，而**不是**屏幕矩形；两者在设置页宽度上一致，但写成按覆盖层算之后
  换布局不会错。

## 验收标准

- **真机录屏**：扩散过程截图判不了（前后帧都没有中间态，`CHANGELOG.md:635` 同因）。
  **已录**（PLK110 release，`build/walk/ripple.mp4`）：单圆盘从点击点扩散，
  真实配色在 t = 0 已生效（第一帧就是新配色，涟漪只是覆盖层）。
  这一条现在能做的根因也记一下：手机自带 `screenrecord` 是**可变帧率**，
  动画期间中位 8.4ms/帧（≈119fps），不像模拟器那样被抽到 1.4–2.8fps。
  上一版"只能真机"的判断方向是对的，当时没量到只是因为设备掉线。
- 连点两个色板：涟漪从新的点击点重新起跳，不出现两圈叠加。
  **已录**（`build/walk/dbltap.mp4`）：连点只看到**一个**环，且它在新点重启。
- 系统动画缩放置 0 时不画涟漪，配色仍然立刻生效。
  由 `MotionScaleUiTest` 判（注入的是应用内部 scale，模拟器与真机等价）。
  注意真机这一轮**只在 1.0 一档跑过**，见 `../CHANGELOG.md` 的「未完成」。
