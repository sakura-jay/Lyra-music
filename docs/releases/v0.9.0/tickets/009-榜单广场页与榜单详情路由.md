# 榜单广场页（来源分段 + 卡片网格）+ 榜单详情路由

**Blocked by**: 006

## 目标
新页「榜单广场」：按来源分段罗列全部榜单卡片；点卡片进该榜曲目列表（**分页详情页**，见"涉及层"里对
`TrackListScreen` 无分页这一约束的处理）。

## 涉及层
- [ ] UI 层：新增 `LeaderboardSquareScreen`（与 `PlaylistSquareScreen` 同级）：来源分段 + 卡片网格。**避免嵌套滚动容器**——整页 `LazyVerticalGrid`（来源标题作横跨整行的 header item），或段内用非滚动 `FlowRow`；**不要** `LazyColumn` 里套 `LazyVerticalGrid`。榜卡片带封面（取不到用占位）。
- [ ] 逻辑层：**详情页不能直接套 `TrackListScreen`**——`TrackListViewModel.loader` 是一次性取数、没有分页，而榜有 100–300 首（PLAN 原写"复用 TrackListScreen"是个洞，已更正）。项目里唯一现成可用的分页状态机在 `HomeViewModel`（触底续取、到 total 停、切榜丢弃晚到响应，且有 `HomePagingTest` 覆盖）。做法：把它抽成 `LeaderboardBoardViewModel`（**沿用注入 `fetchBoard: suspend (Board, Int, Int) -> BoardPage` 这个既有接缝**），详情页 = 头部（榜名 + 总数 + 封面）+ 带序号的 `TrackRow` 列表；`TrackListScreen` 那套头部视觉可以照搬，但数据与分页是另一条链。010 之后 `HomeViewModel` 不再需要榜的翻页，顺势瘦身。
- [ ] 导航：注册 `ROUTE_LEADERBOARDS`（广场）+ 榜单详情路由（`LyraApp.kt`）。
- [ ] 测试：纯 JVM——分段 / 分页 / 切来源丢弃晚到响应（沿用 `HomePagingTest` 的靶心，别另起一套）；设备测试——进广场、点卡片进详情、触底翻页、某来源失败只影响该段。

## 封面从哪来（开工前已实测定下，别再当未知项）

三家都没有"一次给全部榜 + 封面"的可用接口，所以广场**不可能一次性拿到所有封面**：

| 来源 | 榜名/榜 id | 榜封面 |
|---|---|---|
| 酷我 | 静态表（`bang_info` 不给榜列表） | 只随 `bang_info` 的 `data.pic` 带回 |
| 酷狗 | 静态表（lx 短 bangid） | `rank/song` 不给榜级图 → 用**榜首歌曲专辑图** |
| 网易云 | 静态表（榜即歌单） | `v6/playlist/detail` 直接给 `coverImgUrl` |

**因此广场按这个形状做**（不是缺陷，是数据现实）：
1. 卡片**先渲染图标占位**（`Board.name` + 短名已经在静态表里，不需要网络）；
2. 某一来源的分段**首次进入可视区**时，才对它那几张榜各发一次"只为取封面"的轻请求
   （酷我 `rn=1`、酷狗 `pagesize=1`、网易云 只读 playlist detail），**并发上限设 3–4**，
   拿到就填图；一个来源 12 张榜，绝不能进页面就 36 连发；
3. 结果按 `board.id` 缓存，滚出滚回不重发；取不到保持占位，不显示破图。
   第 4 条与工单 011 是同一条链：占位期短、复用率高，靠的正是 011 的图片缓存。

## 验收标准
- 榜单广场按来源分段，段内列出该来源**全部**榜卡片（带封面 / 占位，无破图空白）。
- 点卡片进详情，头部 = 榜名 + 总数，曲目行带序号。
- 触底翻页；切榜不串标题与列表。
- 单来源失败不影响其余段（各段空态 / 错误态独立）。
- **进页面不产生 36 个并发请求**：封面请求只发生在分段首次进入可视区，且并发受限、结果复用。
