# 016 共享元素回程缓动

**主交互**：无匹配模式（普通实现）

## 目标

用户反馈："带图片的界面（榜单/歌单/迷你条展开）退出时，返回原位的速度观感不好（感觉是匀速）"。
本片先核实这条反馈，再修。

**核实结论：反馈成立，但"匀速"这个描述不准——真实情况更糟：回程是加速落位。**
封面以最高速撞进来路那张卡片，而那一段正是眼睛盯着的那一段。

## 涉及层

- [x] `ui/common/CoverFlight.kt`：`coverFlightEasing(enter)` 抽成公开纯函数；
  回程从 `FastOutLinearInEasing`（加速）换成 `FastOutSlowInEasing`（减速落位）。
  去程 `LinearOutSlowInEasing` 保持不动。
- [x] `CoverFlightTest` 新增 3 条 JVM：两个方向都必须减速落位、回程不再是加速曲线
  （含变异测试）、曲线端点精确为 0/1。
- [x] 不改飞行时长（large 档 350 入 / 450 出）、不改插值、不改注册/终点追踪。

## 为什么 Material 的"出场用加速"在这里是错的

Material 那套约定（入场减速、出场加速）的前提是**出场的东西会消失**——
加速离开屏幕是对的，因为没人会去看它落在哪儿。

共享元素的回程不消失：它要精确落回一张就在用户眼前的卡片。
最后那一段恰恰是眼睛盯着的那一段，加速曲线等于**以最高速撞进终点**。

换成 `FastOutSlowInEasing`（cubic-bezier，无过冲，符合 ADR-0009 护栏一：
过冲只给小元素）：起步有一小段加速所以不像被拽走，中段最快，尾段减速落位。
去程保持原曲线——那是被认可的那一条，且它本来就是减速落位。

## 真机逐帧测速（PLK110 release 包）

录像 `build/walk/r011.mp4`（改前）与 `build/walk/a016.mp4`（改后），
同一交互（榜单详情 → 返回广场）。封面用模板匹配逐帧定位（`build/ps/ctrace.ps1`，
位移精度 ±2px），时间戳用 `ffprobe` 的真实 `pts_time`（录屏是变帧率，
帧号 × 标称 fps 一律不成立）。

**改前回程**（f105–f133，465ms，位移 206px）：

| 指标 | 值 |
| --- | --- |
| 前 10% 时间走完 | **1%** |
| 半程时走完 | 34% |
| 后 10% 时间走完 | **12.6%** |
| 峰值速度 | 14 px/帧，出现在 **93%** 处（窗口末尾） |

**改后回程**（f113–f134，349ms，位移 202px）：

| 指标 | 值 |
| --- | --- |
| 前 10% 时间走完 | 3% |
| 半程时走完 | **71%** |
| 后 10% 时间走完 | **5%** |
| 峰值速度 | 20 px/帧，出现在 **33%** 处（中段） |

判读：
- **峰值位置从 93% 挪到 33%**——速度曲线从"越走越快"变成"中段最快、两头慢"。
- **尾段位移 12.6% → 5%**——撞进终点的那一下收掉了。
- 首段 1% → 3%：起步比原来略快，这是 `FastOutSlowIn` 的形状（起步有一小段加速），
  观感上"不像被拽走"，与修复目标一致。
- 去程是对照组，改前后都在规格形状内（半程 77–84%、尾段 0–3%），
  说明改动没有外溢到去程。

**±2px 精度的边界要写清**：改后尾段每帧只剩 4–6px 位移，与模板匹配精度同量级。
所以"尾段 12.6% → 5%"这个比的**下界**是可靠的（加速撞进终点确实消失），
但 5% 里的每一帧具体是 4px 还是 6px，这个工具分辨不了。

## 变异测试

把 `coverFlightEasing` 的实现临时改成恒等 `if (true) FastOutLinearInEasing`，
`returnDirectionIsNoLongerTheAcceleratingOne` 当场红；改回后绿。
这条不是推理，是**做过**的。

新断言 `bothDirectionsDecelerateIntoTheTarget` 的判据是"末段位移 < 首段位移"，
不比对具体时长——时长会被录屏帧率影响，这个比值不会。

## 顺带收掉 v0.9.3 的一条未解释项

011 工单记过「`dy=188→…→0` 跨 247ms，与规格 350ms 差约 100ms，未解释」。

**本版重量后发现那个 247ms 本身是错的**，错在两处：
1. 起止帧是**肉眼挑**的，不是差分定义的"第一帧有变化 / 最后一帧有变化"；
2. 模板匹配跨了**三段不连续的录像片段**（f105→f101 有 1.9s 空隙、
   f101→f102 有 1.2s 空隙），这些空隙没剔除，直接当连续动画量了。

同一份录像用正确方法（相邻帧差分定起止、跳变帧剔除、`pts_time` 算间隔）重测：
**去程实际 274–299ms**，落在 large 档规格（350ms 基准 × 系统缩放 1.0，
叠加路由转场与起跑延迟后的可见窗口）。**不是应用快了 100ms，是原来的量法错了。**
011 工单与本版 CHANGELOG 都已订正。

这是本项目第九次抓到"先挑一段看着像在动的帧区间、再把区间跨度当时长"的循环论证
（010 的 324ms、011 的 247ms、014 的 116ms 是最近三次）。判据已经固定：
**起止帧必须由逐帧差分定义，时间必须用 `pts_time`，跳变帧必须剔除。**

## 验收标准

- 回程缓动为减速落位曲线（`FastOutSlowInEasing`）。**读过代码 + JVM 断言钉住。**
- 两个方向都满足"末段位移 < 首段位移"。**JVM 量过（20 采样）。**
- 回程峰值速度出现在中段而非末尾。**真机逐帧量过（93% → 33%）。**
- 去程曲线与观感不变。**真机逐帧量过（对照组）；JVM 断言 `retHead <= fwdHead`。**
- 全屏位移无过冲（ADR-0009 护栏一）。**读过代码：cubic-bezier 无过冲。**
- JVM 140 条全绿（`--rerun-tasks`）。**量过。**
- instrumented 172 条全绿（emulator-5554）。**量过。**
